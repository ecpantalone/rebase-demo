git config --global core.editor "code --wait"

The --wait flag is important as it tells the terminal to wait until you close the file in VSCode before proceeding with the Git operation.

INTERACTIVE REBASE PROTOCOL

To use interactive rebase, be sure to add any changes that may exist and then:

git rebase -i HEAD~n

Where n is the number of commits you want to modify.

Alternatively, to rebase onto another branch:

git rebase -i <branch-name>

i
Rebasing should nearly never be performed on your main branch. I always rebase to another branch and never perform this in the main branch itself.

This will open the interactive rebase editor in VSCode, showing a list of commits with actions:

pick Use the commit as is
reword Edit the commit message
edit Pause to amend the commit
squash Combine with previous commit (keeps both messages)
fixup Combine with previous commit (discards this message)
drop Remove the commit entirely

Warning: Rebasing rewrites history. Never rebase commits on a main or shared branch without consulting team members!

PERSONAL LOG ENTRY

I especially am fond of fixup to combine the contents of commits to another commit message. Why? Because no one needs to know I was fixing a typo. It's not relevant to the person performing a code review for me or even to me in 3 years when I'm trying to retrace my steps.

FINALIZING THE REBASE SEQUENCE

Once all commits have been changed in the way you want, click 'Start Rebase'. This will ideally result in a clean process, but can trigger merge conflicts, depending on how many changes you made at once.

I prefer to make small changes and then use fixup later to clean things up a bit. Once you see in the terminal successful rebase, it is time to push.

You must force push this commit, because we are rewriting history. I prefer to run:

git push origin HEAD --force-with-lease

i
The --force-with-lease flag is safer than --force as it will abort if there have been any upstream changes you haven't pulled.
